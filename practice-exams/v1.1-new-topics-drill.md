### Question 1
A retail company streams order events through Amazon Data Firehose into an Apache Iceberg table in an S3 general-purpose bucket. The table is registered in the AWS Glue Data Catalog. Dashboards in Amazon Athena must show new orders within 5 minutes. After six weeks, Athena queries against the table have become slow. Investigation shows tens of thousands of small data files, many position-delete files from Firehose updates, and thousands of snapshots. The data must stay in the current bucket because existing S3 replication and lifecycle rules depend on it.

Which solution will fix the performance problem with the LEAST operational overhead?

- **A.** Create an Amazon EventBridge Scheduler schedule that starts an AWS Step Functions workflow every night. The workflow runs Athena `OPTIMIZE ... REWRITE DATA USING BIN_PACK` and then `VACUUM` against the table.
- **B.** Raise the Firehose buffering hints to 128 MiB and 900 seconds so that Firehose commits fewer, larger files to the table.
- **C.** Enable the AWS Glue Data Catalog table optimizers for compaction, snapshot retention, and orphan file deletion on the table.
- **D.** Create an Amazon S3 table bucket, migrate the table into it with an Athena CTAS statement, and point the Firehose stream at the new table.

<details>
<summary><b>Show answer</b></summary>

**Answer: C**

**Why C:** Firehose commits files and snapshots but never compacts or expires them on a self-managed Iceberg table. Glue Data Catalog table optimizers are the managed way to run the three maintenance tasks on Iceberg tables in general-purpose buckets. Compaction merges small files and applies the delete files, snapshot retention expires old snapshots, and orphan file deletion removes unreferenced files. It's a per-table setting with no jobs or schedules to maintain.

**Why not the others:**
- **A** — It works, but you build and operate a scheduler, a workflow, IAM permissions and error handling. That's more overhead than turning on a managed optimizer.
- **B** — A 900-second buffer breaks the 5-minute freshness requirement. It also does nothing about the files, delete files and snapshots that already exist.
- **D** — S3 Tables would maintain the table automatically, but the stem says the data must stay in the current bucket. A migration is also more work than a configuration change.

**Signal words:** *"small data files"*, *"position-delete files"*, *"must stay in the current bucket"*, *"LEAST operational overhead"* · **Skill:** 2.1.7 · **Review:** [Guide 04 — Open Table Formats & S3 Tables](../topic-guides/04-Open-Table-Formats-S3-Tables.md)
</details>

### Question 2
A telecom company has 40 million customer-support transcripts stored as text files in Amazon S3. A data engineer must add a sentiment label and a product category to every transcript and load the results into Amazon Redshift. The labels are needed for a report at the end of the week. There is no latency requirement for individual transcripts.

Which approach will meet these requirements MOST cost-effectively?

- **A.** Write the prompts as JSONL records in Amazon S3, submit Amazon Bedrock batch inference jobs that write their output to S3, and load the output into Redshift with `COPY`.
- **B.** Run an AWS Glue Spark job with 100 workers that calls the Amazon Bedrock `InvokeModel` API once for each transcript and writes the labels to S3 for a Redshift `COPY`.
- **C.** Purchase Amazon Bedrock Provisioned Throughput for one month, and run the batch inference jobs against the provisioned model so that the jobs have guaranteed capacity.
- **D.** Configure S3 Event Notifications to invoke an AWS Lambda function for each transcript. The function calls Amazon Bedrock on-demand and inserts the labels into Redshift through the Redshift Data API.

<details>
<summary><b>Show answer</b></summary>

**Answer: A**

**Why A:** This is a large offline job with a loose deadline, which is exactly what Bedrock batch inference is for. You put one JSON record per prompt in S3 files (`{"recordId": ..., "modelInput": {...}}`), submit jobs, and the results land in S3. Batch inference costs about 50% less than on-demand for supported models, and Bedrock manages the throughput, so you don't fight throttling.

**Why not the others:**
- **B** — 100 workers calling `InvokeModel` in parallel will hit the per-model TPM/RPM quotas and cause `ThrottlingException` storms. Every call is also billed at the full on-demand price.
- **C** — Batch inference can't run on Provisioned Throughput models. A month of model units would also cost far more than a one-off job needs.
- **D** — It's on-demand pricing again, plus 40 million Lambda invocations and row-by-row inserts into Redshift. That's the most expensive design here.

**Signal words:** *"40 million"*, *"end of the week"*, *"no latency requirement"*, *"MOST cost-effectively"* · **Skill:** 1.2.10 · **Review:** [Guide 19 — GenAI, LLMs & Vectors](../topic-guides/19-GenAI-LLMs-Vectors.md)
</details>

### Question 3
A media company is building a recommendation feature on Amazon OpenSearch Service. The vector index starts empty on launch day and then receives a continuous stream of new item embeddings, growing to about 80 million vectors. Queries must return the highest possible recall at the lowest query latency. The team has budgeted for memory-optimized instances, so memory use isn't a constraint.

Which index configuration should the data engineer choose?

- **A.** An IVF index with the Faiss engine, trained with the Train API on the first day's embeddings.
- **B.** Exact k-NN search with a script score query over the `knn_vector` field and no approximate index, because exact search always returns 100% recall.
- **C.** An IVF index with product quantization (IVF-PQ), so that more of the index fits in memory and each query touches fewer vectors.
- **D.** An HNSW index with the Faiss engine.

<details>
<summary><b>Show answer</b></summary>

**Answer: D**

**Why D:** HNSW is a multi-layer proximity graph. It gives the best recall and the lowest latency of the approximate index types. It needs **no training step**, so you can create it on an empty index and insert vectors as they arrive. Its costs are the most memory and the slowest builds, and the stem removes memory as a constraint.

**Why not the others:**
- **A** — IVF has to be trained on representative data. Centroids learned from day one's embeddings go stale as the collection grows 80-fold, and recall drops unless you retrain.
- **B** — Exact search does return 100% recall, but its cost grows linearly with the number of vectors. At 80 million vectors it can't meet "lowest query latency."
- **C** — Product quantization is the lowest-memory option, but it's lossy and has the lowest recall. It also needs training. It fits a tight memory budget, which this team doesn't have.

**Signal words:** *"starts empty"*, *"continuous stream"*, *"highest possible recall at the lowest query latency"*, *"memory isn't a constraint"* · **Skill:** 2.1.8 · **Review:** [Guide 19 — GenAI, LLMs & Vectors](../topic-guides/19-GenAI-LLMs-Vectors.md)
</details>

### Question 4
A manufacturing company runs one Amazon SageMaker Unified Studio domain for its Finance, Marketing, and Supply Chain business units. Today only the two domain administrators can decide who creates projects, and they have become a bottleneck. Each business unit's data lead must be able to decide which users and groups can create projects in that business unit. The leads must not get administrative control over the domain or over the other business units.

Which solution will meet these requirements?

- **A.** Add each business unit's data lead as a domain administrator, and ask the leads to create projects only for their own business unit.
- **B.** Create a domain unit for each business unit under the root domain unit, make each data lead the owner of that domain unit, and let the leads grant project creation policies to the users and groups they choose.
- **C.** Attach IAM policies to the business unit users' roles that allow project creation actions only when a business-unit resource tag matches the user's department tag.
- **D.** Create a separate IAM-based domain for each business unit in the same AWS account, and make each data lead the administrator of that business unit's domain.

<details>
<summary><b>Show answer</b></summary>

**Answer: B**

**Why B:** Domain units exist to delegate authority. They form a hierarchy under the root unit that mirrors the organization, and a **domain unit owner** manages authorization policies for that unit only. The **project creation policy** says which users and groups can create projects in that unit. The leads get exactly the control they need, and domain-wide settings stay with the domain administrators.

**Why not the others:**
- **A** — Domain administrators control the whole domain: project profiles, blueprints, account associations and every business unit. That breaks the least-privilege requirement, and "please only touch your own unit" isn't a control.
- **C** — Who can create projects inside Unified Studio is governed by domain unit authorization policies. IAM tag conditions on individual roles don't replace that model and are harder to maintain.
- **D** — Only one IAM-based domain is allowed per AWS account. Separate domains would also split the catalog, so the business units couldn't discover and share each other's data in one place.

**Signal words:** *"each business unit's data lead"*, *"decide which users and groups can create projects"*, *"must not get administrative control over the domain"* · **Skill:** 4.1.7 · **Review:** [Guide 41 — SageMaker Unified Studio, Catalog & Governance](../topic-guides/41-SageMaker-Unified-Studio-Catalog-Governance.md)
</details>

### Question 5
An insurance company built an Amazon Bedrock knowledge base over 3,000 policy manuals in Amazon S3. The vector store is an Amazon OpenSearch Serverless vector collection. The data source uses fixed-size chunking of 300 tokens. Users report that the retrieved chunks match their questions precisely, but the answers are often incomplete because the surrounding clauses of the policy are missing.

Which change will MOST effectively fix this problem?

- **A.** Update the existing data source's chunking configuration to hierarchical chunking, and then start a sync so that only the changed documents are re-chunked.
- **B.** Create a new data source for the same S3 location with hierarchical chunking, run a sync to ingest it, and then remove the original data source.
- **C.** Recreate the data source with no chunking so that each manual is embedded as a single chunk and the model always receives the full document.
- **D.** Increase the number of results that each `RetrieveAndGenerate` call returns from 5 to 50 so that more chunks reach the model.

<details>
<summary><b>Show answer</b></summary>

**Answer: B**

**Why B:** **Hierarchical chunking** searches small **child** chunks for precise matches and returns their larger **parent** chunks, so the model gets the surrounding context. That's the exact fix for "precise but incomplete." The chunking strategy is fixed when a data source is created, so you need a new data source and a re-ingestion. The OpenSearch Serverless store is a good fit. Hierarchical chunking isn't recommended with S3 Vectors because of its per-vector metadata limits, but that isn't the store here.

**Why not the others:**
- **A** — You can't change the chunking strategy of an existing data source. A sync also only reprocesses new, changed or deleted documents, not the whole corpus.
- **C** — One vector for a whole manual blurs matching badly. Long manuals also go past the embedding model's input limit (8,192 tokens for Titan Text Embeddings V2), and you lose page-level citations.
- **D** — More results adds noisy, loosely related chunks and more tokens. The chunks still don't contain the clauses around each match.

**Signal words:** *"match their questions precisely"*, *"surrounding clauses … missing"* · **Skill:** 2.4.6 · **Review:** [Guide 19 — GenAI, LLMs & Vectors](../topic-guides/19-GenAI-LLMs-Vectors.md)
</details>

### Question 6
A payments company is building a real-time fraud-scoring API. Each request must find the most similar past transactions by vector similarity in single-digit milliseconds, with recall above 99%. The same service must also read and write per-customer session data as key/value pairs with microsecond read latency. All data must survive a node failure without loss, and the team wants to operate a single data store.

Which solution will meet these requirements?

- **A.** Store the transaction embeddings in an Amazon S3 Vectors index and the session data in an Amazon DynamoDB table.
- **B.** Deploy an Amazon ElastiCache (Valkey) cluster as the only data store for both the vectors and the session data, and take automatic daily snapshots to protect the data.
- **C.** Create an Amazon MemoryDB cluster with vector search enabled at creation, build an HNSW index for the embeddings, and store the session data as key/value pairs in the same cluster.
- **D.** Store the embeddings in Amazon Aurora PostgreSQL with a pgvector HNSW index, and put an Amazon ElastiCache cluster in front of Aurora for the session data.

<details>
<summary><b>Show answer</b></summary>

**Answer: C**

**Why C:** MemoryDB is an in-memory database that is also **durable**. Every write goes to a Multi-AZ transaction log before it's acknowledged, so it can be the system of record. Its vector search (FLAT and HNSW) returns results in single-digit milliseconds at more than 99% recall, and key/value reads take microseconds. Vector search has to be turned on when the cluster is created and runs on a single shard.

**Why not the others:**
- **A** — S3 Vectors is built for low cost at sub-second latency (about 100 ms for frequent queries), not single-digit milliseconds. It also means running two stores.
- **B** — ElastiCache is a cache. Daily snapshots lose every write since the last snapshot, so it doesn't meet "survive a node failure without loss" as the only data store.
- **D** — Aurora with pgvector is a good vector store, but this design runs two services, and the cache layer has the same durability gap as B.

**Signal words:** *"single-digit milliseconds"*, *"recall above 99%"*, *"microsecond read latency"*, *"survive a node failure without loss"*, *"single data store"* · **Skill:** 2.1.3 · **Review:** [Guide 28 — RDS, Aurora & Purpose-Built Databases](../topic-guides/28-RDS-Aurora-Purpose-Built-DBs.md)
</details>

### Question 7
A healthcare company stores patient engagement data in an Apache Iceberg table in an S3 general-purpose bucket. S3 Versioning isn't enabled on the bucket. Amazon Athena is the only engine that writes to the table. A patient invoked the right to erasure. The data engineer ran `DELETE FROM engagement WHERE patient_id = 'P-1042'`, and the row no longer appears in query results. The legal team requires that the patient's data be physically removed from Amazon S3, including from every historical version of the table.

Which combination of additional actions will meet this requirement? (Select TWO.)

- **A.** Run the Iceberg `rollback_to_snapshot` procedure to return the table to the snapshot before the patient's first record was written.
- **B.** Run `OPTIMIZE engagement REWRITE DATA USING BIN_PACK` on the affected partitions so that the data files are rewritten without the deleted rows.
- **C.** Create an AWS Lake Formation data filter that excludes `patient_id = 'P-1042'`, and grant all analysts access through the filter.
- **D.** Set the table's `vacuum_max_snapshot_age_seconds` property to a short value, and then run `VACUUM engagement` to expire older snapshots and remove files that are no longer referenced.
- **E.** Increase the table's `vacuum_min_snapshots_to_keep` property to 10 so that `VACUUM` keeps enough history for audits.

<details>
<summary><b>Show answer</b></summary>

**Answer: B, D**

**Why B and D:** Athena's `DELETE` uses merge-on-read. It writes a position-delete file that hides the row, but the original data file still holds the bytes, and older snapshots still point to it. First, `OPTIMIZE` compacts the files and applies the delete files, so the current snapshot references new data files without the row (**B**). Then `VACUUM` with a short snapshot age expires the snapshots that still reference the old files and removes the orphaned files from S3 (**D**). The full purge sequence is **DELETE → compact → expire snapshots → remove orphan files**. `VACUUM` needs `s3:DeleteObject`, or it "succeeds" without deleting anything.

**Why not the others:**
- **A** — A rollback moves the current pointer back to an old snapshot. It throws away every legitimate change since then and doesn't delete any file.
- **C** — A data filter hides the rows from queries. The bytes are still in S3, so it isn't erasure.
- **E** — Keeping more snapshots is the opposite of what's needed. Old snapshots are exactly what keeps the patient's data reachable.

**Signal words:** *"right to erasure"*, *"physically removed"*, *"every historical version"* · **Skill:** 2.1.7 · **Review:** [Guide 04 — Open Table Formats & S3 Tables](../topic-guides/04-Open-Table-Formats-S3-Tables.md)
</details>

### Question 8
A bank publishes data assets to Amazon SageMaker Catalog from several producer projects. The governance team requires that every table published to the catalog record a data classification (one of Public, Internal, Confidential, or Restricted) and a retention period in months. Producers must not be able to publish an asset until both values are filled in.

Which solution will meet these requirements with the LEAST operational overhead?

- **A.** Create a metadata form in the domain with a classification field that allows only the four values and a numeric retention field. Configure the form as required for published table assets.
- **B.** Create business glossary terms named Public, Internal, Confidential, and Restricted, and tell producers to attach one term to each asset before they publish it.
- **C.** Add `classification` and `retention` table properties to each table in the AWS Glue Data Catalog, and deploy an AWS Config custom rule that flags tables where either property is missing.
- **D.** Apply AWS Lake Formation LF-Tags for classification and retention to each table, and run a nightly AWS Lambda function that unpublishes any catalog asset without both tags.

<details>
<summary><b>Show answer</b></summary>

**Answer: A**

**Why A:** **Metadata forms** are domain-defined templates with typed fields. A field can be limited to a set of allowed values or to numbers, and a form can be **required** before an asset is published. That enforces the rule inside the catalog workflow itself, with no custom code.

**Why not the others:**
- **B** — Glossary terms give the company a shared vocabulary. They aren't typed fields, they can't hold a retention value, and attaching them isn't enforced.
- **C** — Glue table properties are technical metadata, and a Config rule only reports problems after the fact. It doesn't block publishing, and it needs custom rule code.
- **D** — It catches missing values only after publishing, up to a day late. It also means building and running a Lambda function.

**Signal words:** *"must not be able to publish … until both values are filled in"*, *"one of … four values"*, *"LEAST operational overhead"* · **Skill:** 2.2.6 · **Review:** [Guide 41 — SageMaker Unified Studio, Catalog & Governance](../topic-guides/41-SageMaker-Unified-Studio-Catalog-Governance.md)

### Question 9
A hotel group stores 2 million guest reviews in an Amazon Redshift Serverless table. The business analysts know SQL but don't write Python, and the company doesn't want to build a new pipeline. The analysts need a short summary and a sentiment label for each review, produced by a foundation model in Amazon Bedrock, so they can join the results with booking data in Redshift.

Which solution will meet these requirements with the LEAST development effort?

- **A.** Use Redshift ML `CREATE MODEL` with Amazon SageMaker Autopilot to train a sentiment model on the review table, and call the generated prediction function from SQL.
- **B.** `UNLOAD` the reviews to Amazon S3, trigger an AWS Lambda function that calls Amazon Bedrock for each file, and `COPY` the results back into a new Redshift table.
- **C.** Write a Redshift scalar Python UDF that calls the Amazon Bedrock runtime API for each review, and call the UDF in a `SELECT` statement.
- **D.** Use Redshift ML `CREATE EXTERNAL MODEL` with `MODEL_TYPE BEDROCK` and a prompt, and call the resulting SQL function in a `SELECT` statement.

<details>
<summary><b>Show answer</b></summary>

**Answer: D**

**Why D:** `CREATE EXTERNAL MODEL … MODEL_TYPE BEDROCK` registers a Bedrock model as a **SQL function** with a prompt (for example, "Summarize this review and label its sentiment:"). Analysts then call it in ordinary `SELECT` statements and join the output with booking tables. There's no pipeline and no Python. Redshift doesn't charge extra for the integration, but Bedrock bills per token.

**Why not the others:**
- **A** — `CREATE MODEL` with Autopilot **trains** a custom model. It needs labeled training data and can't write summaries. Model training is also outside the exam's scope.
- **B** — It works, but it's the new pipeline the company wants to avoid: an export, a Lambda function, a reload and the orchestration between them.
- **C** — Redshift Python UDFs can't make network calls, and Redshift ended support for Python UDFs after June 30, 2026. The supported way to call an external service from a UDF is a Lambda UDF, which is still more work than D.

**Signal words:** *"know SQL but don't write Python"*, *"doesn't want to build a new pipeline"*, *"LEAST development effort"* · **Skill:** 1.2.10 · **Review:** [Guide 19 — GenAI, LLMs & Vectors](../topic-guides/19-GenAI-LLMs-Vectors.md)

### Question 10
A consumer goods company has 12 business domains, and each domain runs its own AWS account. Today a central data team copies all domain data into one data lake account and builds every dataset, and it has become a bottleneck. The company wants each domain to own and publish its data as products in its own account. A central governance team must still enforce common classification and tagging standards, audit access, and give all consumers one place to discover data.

Which approach meets these requirements?

- **A.** Keep the central data lake account, and add more engineers to the central data team so that it can build domain datasets faster.
- **B.** Let each domain share its S3 buckets directly with the consumer accounts that need them through bucket policies, with no central catalog, so that the domains are fully independent.
- **C.** Set up a central governance account that hosts a SageMaker Catalog domain with the domain accounts associated to it. Keep the data in the producer accounts, and share tables with AWS Lake Formation cross-account grants based on LF-Tags.

**Answer: C**

Lake Formation cross-account sharing gives consumers live, in-place access without copies.

- **B** — That's fully decentralized with **no federated governance**. There's no single place to discover data, and no central enforcement of standards. A data mesh still needs shared governance.

### Question 11
A legal-tech company stores 5 million document embeddings in an Amazon Aurora PostgreSQL table with the pgvector extension. A data engineer created the table and immediately ran `CREATE INDEX ON docs USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100)`, and then bulk-loaded all 5 million rows. Similarity queries with the `<=>` operator are fast, but they often miss documents that exact search returns.

Which combination of actions will improve recall? (Select TWO.)

- **A.** Drop the IVFFlat index and create it again now that the table is loaded, with `lists` set to roughly the square root of the row count (about 2,200).
- **B.** Run `SET hnsw.ef_search = 200` in the session before the similarity queries so that the index search examines more candidates.
- **C.** Increase `ivfflat.probes` from its default of 1, starting at roughly the square root of `lists`, so that each query searches more clusters.
- **D.** Rebuild the index with the `vector_ip_ops` operator class, and change the queries to use `<#>` because inner product returns more accurate neighbors.
- **E.** Move the cluster to instances with Aurora Optimized Reads so that the index can be read from local NVMe storage.

<details>
<summary><b>Show answer</b></summary>

**Answer: A, C**

**Why A and C:** IVFFlat learns its cluster centroids with k-means **when the index is built**. The centroids from an empty table describe nothing, so vectors end up in poorly chosen clusters. Rebuild after loading, with `lists` ≈ √rows once you're past about 1 million rows (**A**). At query time, `ivfflat.probes` controls how many clusters are searched. The default of 1 is fast but gives poor recall, and √lists is the usual starting point (**C**). Switching to HNSW, which needs no training, would also work, but it isn't offered here.

**Why not the others:**
- **B** — `hnsw.ef_search` only affects HNSW indexes. It does nothing for IVFFlat.
- **D** — The operator has to match the metric the embeddings were built for. Inner product isn't "more accurate," and with normalized vectors it gives the same ranking as cosine anyway. It doesn't fix the stale centroids.
- **E** — Optimized Reads can speed up queries when the index is bigger than memory. It doesn't change which neighbors the index returns.

**Signal words:** *"immediately ran CREATE INDEX … ivfflat"*, *"then bulk-loaded"*, *"often miss documents that exact search returns"* · **Skill:** 2.1.8 · **Review:** [Guide 19 — GenAI, LLMs & Vectors](../topic-guides/19-GenAI-LLMs-Vectors.md)
</details>

### Question 12
A financial services company stores its trade tables as Apache Iceberg tables in an Amazon S3 table bucket and leaves the default maintenance settings on. A new audit requirement says analysts must be able to query any table as it looked at any point in the last 30 days by using Iceberg time travel in Amazon Athena. Time-travel queries currently fail for points in time more than about 5 days ago.

Which solution will meet this requirement?

- **A.** Update each table's snapshot management maintenance configuration through the S3 Tables API so that snapshots up to 720 hours old are kept.
- **B.** Run `ALTER TABLE ... SET TBLPROPERTIES ('history.expire.max-snapshot-age-ms' = '2592000000')` on each table so that Iceberg keeps 30 days of snapshots.
- **C.** Turn off unreferenced file removal on the table bucket so that old data files stay in S3 and remain available to time-travel queries.
- **D.** Run a nightly Athena CTAS job that copies each table into a dated backup table, and have auditors query the backup table for the date they need.

<details>
<summary><b>Show answer</b></summary>

**Answer: A**

**Why A:** S3 Tables runs snapshot management for you. By default it keeps at least 1 snapshot and expires snapshots older than **120 hours (5 days)**, which is exactly the failure described. Time travel only reaches snapshots that haven't been expired. In S3 Tables you change retention through the **S3 Tables maintenance configuration** (the table's snapshot management settings), for example 720 hours for 30 days.

**Why not the others:**
- **B** — S3 Tables doesn't read Iceberg table properties such as `history.expire.max-snapshot-age-ms` for its maintenance. This is the common trap for people coming from self-managed Iceberg.
- **C** — Unreferenced file removal only deletes files that no snapshot uses. The snapshots themselves still expire after 120 hours, so time travel still fails.
- **D** — It works, but it creates 30 full copies of every table to pay for and manage. Auditors also lose true point-in-time queries between nightly copies.

**Signal words:** *"S3 table bucket"*, *"default maintenance settings"*, *"more than about 5 days ago"*, *"last 30 days"* · **Skill:** 2.1.7 · **Review:** [Guide 04 — Open Table Formats & S3 Tables](../topic-guides/04-Open-Table-Formats-S3-Tables.md)
</details>

### Question 13
An e-commerce company's product catalog runs on Amazon Aurora PostgreSQL. The company wants semantic product search over 8 million embeddings generated from product descriptions. Each search must combine vector similarity with SQL filters on `price` and `in_stock`, and join with the inventory tables. New products are added all day. Searches need high recall and low latency, and the company wants to add as little new infrastructure as possible.

Which solution meets these requirements?

- **A.** Create an Amazon OpenSearch Service domain for the embeddings, sync product changes to it with a pipeline, and join the search results with the inventory data in the application.
- **B.** Enable the pgvector extension, add a `vector` column for the embeddings, and create an HNSW index with `vector_cosine_ops` on that column.
- **C.** Store the embeddings in an Amazon S3 Vectors index with price and stock as filterable metadata, and look up inventory details in Aurora for each result.
- **D.** Enable the pgvector extension and add a `vector` column, but don't create a vector index, so that every query runs an exact search with perfect recall.

<details>
<summary><b>Show answer</b></summary>

**Answer: B**

**Why B:** pgvector keeps the embeddings **next to the relational data**. One SQL statement can rank by `<=>` (cosine distance), filter on `price` and `in_stock`, and join with inventory tables, with no new service to run. HNSW gives the best recall and latency, and because it needs no training it handles products being inserted all day.

**Why not the others:**
