# 39 · Encryption, KMS & Secrets — the bank vault, the key cabinet, and the password safe

> **Exam map:** D4 · Task 4.1, 4.2, 4.3 · **Skills:** 4.1.3, 4.2.2, 4.3.2, 4.3.3, 4.3.4 · **Weight:** 🔥🔥🔥 High · **Read time:** ~22 min

## The idea

Picture a **bank**. Deep in the vault sits a **master key** that **never leaves the vault**. That's a **KMS key** (AWS Key Management Service), held inside hardware security modules (HSMs). You can't take it home. You can only send a clerk requests like *"encrypt this small note"* or *"give me a fresh small key, and a copy of it locked with the master key."*

That small key is a **data key**. You use it at your desk to lock your large boxes of data, throw the plain data key away, and **store the locked copy of the data key next to the box**. To open the box later, you send the locked copy back to the vault, the clerk unlocks it with the master key (if the rulebook, the **key policy**, allows you), and hands you the plain data key for a moment. This is **envelope encryption**, and nearly every AWS service does it for you: S3, Redshift, Glue, EMR, Kinesis, DynamoDB.

Next to the vault is a **password safe** for things that aren't encryption keys at all: database passwords, API tokens, connection strings. That's **AWS Secrets Manager** (with automatic rotation), with its cheaper sibling **Systems Manager Parameter Store** for configuration.

The exam tests four kinds of question: *which key type* (and who controls it), *why an access or cross-account request fails* (the key policy), *how each data service encrypts at rest and in transit*, and *where to keep and rotate credentials*. This guide covers all four.

## KMS key types: who owns the key?

| | **AWS owned keys** | **AWS managed keys** (`aws/s3`, `aws/redshift`, `aws/kinesis`…) | **Customer managed keys (CMKs)** |
|---|---|---|---|
| Lives in your account? | No (shared across AWS) | Yes, visible in the console | Yes |
| Key policy | Not visible | Visible but **not editable** | **You write it** |
| Rotation | Service decides | **Automatic every year** (not configurable) | **Optional**: automatic every **90–2,560 days** (default **365**) and/or **on-demand** |
| CloudTrail visibility of use | No | Yes | Yes |
| Cross-account use | No | **No** | **Yes** |
| Cost | Free | No monthly fee (API usage may bill) | Monthly fee per key + API requests |
| Pick when | "Encrypt, don't care" (e.g., DynamoDB default) | Simple audited encryption within one account | **Control, separation of duties, cross-account, custom rotation, disable/delete on demand** |

**THE trap:** *"Share encrypted data (an S3 bucket, a Kinesis stream, a secret, an RDS snapshot) with another account; the consumer gets AccessDenied on KMS."* If the data is encrypted with an **AWS managed key**, it can't work, because you can't edit that key policy to add the other account. **Re-encrypt with a customer managed key** and grant the other account in its key policy.

**Key specs and origins**
- **Symmetric** (AES-256, the default; used by all service integrations), **asymmetric** (RSA/ECC for encrypt or sign/verify; the public key can be downloaded and used outside AWS), **HMAC** (generate/verify MACs, for tamper-evident tokens).
- **Key material origin:** generated by KMS (`AWS_KMS`); **imported / BYOK** (`EXTERNAL`: you keep a copy and can set an expiry; no automatic rotation, on-demand only); **AWS CloudHSM key store** (a custom key store backed by your own CloudHSM cluster); **external key store (XKS)** (key material stays in an HSM **outside AWS**, which answers *"keys must never be stored in AWS"*).
- **Multi-Region keys:** related keys with the **same key ID and material** in several Regions. Data encrypted in one Region can be decrypted in another **without a cross-Region KMS call or re-encryption**. Used for DR, global tables and client-side encryption across Regions. Each replica is still its own resource with its own key policy.
- **Deleting a key:** schedule deletion with a **7–30 day waiting period (default 30)**. Once deleted, data encrypted under it is **gone forever**. Safer alternatives: **disable** the key, and alarm on attempted use during the waiting period.
- **Rotation keeps the same key ID/ARN.** KMS keeps old material to decrypt old ciphertext. It does **not** re-encrypt existing data. Asymmetric keys, HMAC keys and custom key stores need **manual** rotation (a new key + alias swap).

## Envelope encryption, limits and throttling

```
Encrypt:  GenerateDataKey(KMS key) ─► plaintext data key  +  encrypted data key
          plaintext data key encrypts the data locally (AES-GCM), then is discarded
          store: [ciphertext data] + [encrypted data key]

Decrypt:  Decrypt(encrypted data key) ─► plaintext data key ─► decrypt data locally
```

- **`Encrypt` accepts at most 4 KB (4,096 bytes)** of plaintext with a symmetric key. **THE trap:** *"Call kms:Encrypt on each 50 MB file."* It fails. Anything bigger than a password or token uses **`GenerateDataKey`** (envelope encryption), which the **AWS Encryption SDK** does for you.
- **Encryption context:** non-secret key-value pairs bound to the ciphertext as additional authenticated data (AAD). Decryption must supply the **exact same** context. It appears in **CloudTrail**, and it can be required in policies (`kms:EncryptionContext:<key>`). S3 uses the bucket/object ARN as the context. Never put secrets in it.
- **Request quotas:** symmetric cryptographic operations share a per-account, per-Region quota of **10,000 / 20,000 / 100,000 requests per second** depending on the Region (us-east-1, us-west-2 and eu-west-1 are at 100,000). Calls AWS services make **on your behalf count**. Cross-account calls count against the **caller's** account. Exceeding the quota returns **`ThrottlingException`**.
- **Fixes for throttling:** **S3 Bucket Keys** (S3 derives object keys from a bucket-level key, cutting KMS calls, and cost, by up to about **99%**; CloudTrail then shows fewer, bucket-level KMS events), **data key caching** in the Encryption SDK, exponential backoff, or a quota increase.

## Who may use a key: key policies, IAM, grants

- **Every KMS key has exactly one key policy**, and it is the **primary** control. The **default key policy** contains a statement that trusts the account root (`"AWS": "arn:aws:iam::111111111111:root"`). That statement **delegates to IAM**: IAM policies in that account can then grant key use. Remove it, and IAM policies alone can't grant access.
- **IAM policies** grant `kms:Decrypt` and similar actions, **but only if the key policy lets IAM decide**.
- **Grants** are temporary, programmatic delegations (`CreateGrant`), used heavily by services (EBS, RDS, Redshift) to use your key on your behalf, and they can be retired.
- **Condition keys:** `kms:ViaService` (usable only through S3/Glue/…), `kms:CallerAccount`, `kms:EncryptionContext:…`, `kms:GrantIsForAWSResource`.

**Cross-account encryption (4.3.3): two statements, two accounts.**

```json
// Key policy statement in the KEY-OWNER account (111111111111)
{
  "Sid": "AllowAnalyticsAccountToUseTheKey",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::222222222222:root" },
  "Action": ["kms:Decrypt", "kms:DescribeKey", "kms:GenerateDataKey*", "kms:ReEncrypt*"],
  "Resource": "*"
}
```

```json
// IAM policy on the consuming role in account 222222222222
{
  "Effect": "Allow",
  "Action": ["kms:Decrypt", "kms:DescribeKey", "kms:GenerateDataKey*"],
  "Resource": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
}
```

In a key policy, `"Resource": "*"` means *this key*. Trusting the other account's root delegates the decision to that account's IAM admins. To be stricter, name specific role ARNs. Cross-account callers must reference the **key ARN** (aliases don't resolve across accounts). The data-side permission (bucket policy, Lake Formation grant, datashare) is still separate ([Guide 37](37-IAM-for-Data-Engineers.md)).

## Service-by-service encryption

| Service | At rest | In transit / enforcement | Must-know notes |
|---|---|---|---|
| **S3** | **SSE-S3 is the default** for all new objects; SSE-KMS; **DSSE-KMS** (dual-layer, for compliance that demands two layers); SSE-C (you send the key on each request, HTTPS only); client-side | Bucket policy **Deny `aws:SecureTransport = false`** | Default encryption applies to **new** writes; existing objects → **S3 Batch Operations** copy. Force a key: deny `PutObject` unless `s3:x-amz-server-side-encryption = aws:kms` (and the key ID). Bucket Keys for KMS cost |
| **Redshift** | KMS (AWS owned, AWS managed or CMK). **New clusters/workgroups are encrypted by default since Jan 10, 2025** | `require_ssl` (default `true` in `default.redshift-2.0`) | An **existing unencrypted cluster can be modified to enable encryption** (Redshift migrates the data; there's a read-only window). Cross-Region snapshot copy of a KMS cluster needs a **snapshot copy grant** in the destination Region. `UNLOAD … ENCRYPTED KMS_KEY_ID '…'` for exported files |
| **EMR** | **Security configuration**: EMRFS on S3 (**SSE-S3, SSE-KMS, CSE-KMS, CSE-Custom**); **local disk** (EBS/instance store via KMS or a custom key provider) | TLS in transit (certificates from a PEM zip in S3 or a custom provider) | One reusable security configuration per cluster also holds Kerberos and Lake Formation settings ([Guide 15](15-Amazon-EMR.md)) |
| **Glue** | **Security configuration** on jobs/crawlers: **S3 targets** (SSE-S3/SSE-KMS), **CloudWatch Logs** (KMS), **job bookmarks** (CSE-KMS). **Data Catalog settings**: metadata encryption + **connection password encryption** (KMS) | JDBC SSL option on connections | Catalog encryption protects databases, tables, partitions and connection passwords at rest |
| **Kinesis Data Streams** | **SSE with KMS** (`aws/kinesis` or CMK), applied as records enter the stream | TLS endpoints | Producers/consumers need `kms:GenerateDataKey`/`kms:Decrypt`; a CMK is needed for cross-account |
| **Firehose** | SSE for the delivery stream's buffered data (AWS owned key or CMK); plus the destination's encryption (S3 SSE-KMS key setting) | TLS | With a Kinesis stream as the source, the stream's SSE applies |
| **MSK** | KMS at rest (AWS managed default or CMK) | **TLS client-broker** (`TLS`, `TLS_PLAINTEXT`, `PLAINTEXT`) + **TLS within the cluster** | mTLS/SASL/IAM for auth ([Guide 08](08-Amazon-MSK-Kafka.md)) |
| **Athena** | **Query results**: SSE-S3, SSE-KMS or CSE-KMS | TLS | **Workgroup setting "override client-side settings"** enforces result encryption for everyone. Reading SSE-KMS source data needs `kms:Decrypt` |
| **DynamoDB** | **Always encrypted**; choose AWS owned (default), AWS managed, or CMK | TLS | **AWS Database Encryption SDK** for client-side, attribute-level encryption |
| **RDS / Aurora** | KMS, **chosen at creation only** | Force SSL (`rds.force_ssl` for PostgreSQL, `require_secure_transport` for MySQL) | Encrypt an existing DB: **snapshot → copy snapshot with encryption → restore**. Read replicas follow the source's encryption |
| **Lambda** | Environment variables encrypted at rest (AWS managed key by default; CMK optional) | — | Console *encryption helpers* encrypt values client-side, so they aren't visible in plaintext in the console |
| **SQS / SNS** | SQS: **SSE-SQS** (default) or SSE-KMS. SNS: SSE-KMS | Deny `aws:SecureTransport = false` | Producers (e.g., S3 events, EventBridge) need KMS permission on a CMK through the key policy |
| **CloudWatch Logs** | Associate a **KMS key with the log group** | TLS | The key policy must allow the `logs.<region>.amazonaws.com` principal |
| **OpenSearch Service** | Encryption at rest (KMS) | **Node-to-node encryption** + **require HTTPS** | Fine-grained access control requires both ([Guide 29](29-OpenSearch-Service.md)) |

**THE trap (RDS):** *"Enable encryption on the running unencrypted RDS instance."* There's no such switch. Use **snapshot → encrypted copy → restore**, then cut over. Redshift **can** be modified in place, which is why the question's service matters.

## In transit vs *before* transit (4.3.4)

> 🆕 **New in exam guide v1.1:** skill 4.3.4 now reads *"encryption in transit or **before** transit"*, which means client-side encryption is explicitly testable.

- **In transit** = TLS on the wire: HTTPS endpoints, `aws:SecureTransport` policies, `require_ssl`, MSK TLS, JDBC SSL, VPN/MACsec for hybrid links ([Guide 38](38-Networking-for-Data-Pipelines.md)). A private network path is **not** encryption.
- **Before transit** = **client-side encryption**: data is encrypted **before it leaves your application**, so AWS stores and moves only ciphertext.

| | **Server-side** (SSE-S3/KMS, Redshift, DynamoDB…) | **Client-side** |
|---|---|---|
| Where encryption happens | In the AWS service, after it receives the data | In your application, before sending |
| Who holds the keys | AWS (KMS keys you may control) | You (KMS via SDK, or your own keys) |
| Does AWS ever see plaintext? | Yes, briefly, inside the service | **Never** |
| Effort | A checkbox | Code/SDK changes; queries on encrypted fields are limited |
| Tools | Service settings | **AWS Encryption SDK** (general data, envelope + data key caching), **Amazon S3 Encryption Client**, **AWS Database Encryption SDK** (DynamoDB attribute-level, searchable encryption), EMR CSE-KMS/CSE-Custom, Athena CSE-KMS |

Signal: *"The provider must never have access to unencrypted data"* or *"encrypt sensitive fields before they are sent to AWS"* → **client-side encryption**. *"Encrypt at rest with the least effort"* → server-side (usually already on by default).

## AWS Secrets Manager (4.1.3, 4.2.2)

The password safe for **credentials that must be rotated**:
- Stores database credentials, API keys, OAuth tokens (up to **64 KB** per secret), always **encrypted with KMS** (`aws/secretsmanager` or a CMK).
- **Automatic rotation** on a schedule from **every 4 hours** to **999 days** (`rate()` or `cron()` expressions, rotation window of at least 1 hour):
  - **Managed rotation**: the service rotates for you, no Lambda. This includes **RDS/Aurora and Redshift admin passwords managed in Secrets Manager** (the *manage master password* option at creation/modify), with no rotation function to maintain.
  - **Lambda rotation functions**: AWS templates for RDS, Aurora, Redshift and DocumentDB (**single-user** or **alternating-users** strategy), or your own function for third-party APIs. Rotation follows the steps createSecret → setSecret → testSecret → finishSecret with staging labels `AWSCURRENT`/`AWSPENDING`/`AWSPREVIOUS`. A rotation Lambda in a private subnet needs a Secrets Manager endpoint and network reach to the database.
- **Cross-account access:** a **resource policy on the secret** + a **customer managed KMS key** whose policy allows the other account (the AWS managed key can't be shared). The consuming role also needs `secretsmanager:GetSecretValue` in its own IAM policy.
- **Multi-Region replication:** replica secrets for DR, kept in sync with the primary.
- **Integrations to remember:** **Glue connections** (JDBC credentials from a secret), **Redshift Data API** (`--secret-arn`), **Redshift federated queries** (the external schema references a secret), **DMS endpoints**, **MWAA** (Secrets Manager as the Airflow secrets backend for connections/variables), **Athena federated query connectors**, **EMR**, **Lambda** (via the extension/caching client), CloudFormation dynamic references `{{resolve:secretsmanager:…}}`.
- Costs a monthly fee per secret plus API calls. Use client-side **caching** to cut calls and latency.

## Systems Manager Parameter Store

| | **Standard** | **Advanced** |
|---|---|---|
| Parameters per account/Region | **10,000** | **100,000** |
| Max value size | **4 KB** | **8 KB** |
| Parameter policies (expiration, notifications) | No | **Yes** |
| Cross-account sharing | No | Yes |
| Cost | **No additional charge** | Charged per parameter + API interactions |
| Change tier | Can upgrade → Advanced | **Can't downgrade** (delete and recreate) |

- Types: `String`, `StringList`, **`SecureString`** (encrypted with KMS, `aws/ssm` or a CMK; decrypt with `--with-decryption`).
- **Hierarchies:** `/prod/etl/orders/db_host`. Fetch a whole subtree with `GetParametersByPath` and scope IAM to a path (`arn:aws:ssm:…:parameter/prod/etl/*`). Versioned history and labels.
- **THE trap:** *"Rotate the database password every 30 days automatically with the least effort"* → **Secrets Manager**. **Parameter Store has no native rotation** (you'd build EventBridge + Lambda yourself). Parameter Store wins for *"free / cheap storage of configuration values and non-rotating secrets."*
- Parameter Store can **reference Secrets Manager** secrets: `/aws/reference/secretsmanager/<secret-name>`, so apps can use one API for both.

**Choosing:**
| Signal | Pick |
|---|---|
| Automatic rotation, DB credentials, RDS/Redshift native integration | **Secrets Manager** |
| Cross-account or multi-Region secret distribution | **Secrets Manager** |
| Config values, feature flags, endpoints, hierarchical settings, lowest cost | **Parameter Store** (Standard) |
| Encrypted static value, no rotation, no extra cost | **Parameter Store SecureString** |

## AWS CloudHSM (one paragraph)

**CloudHSM** gives you **dedicated, single-tenant HSMs** in your VPC, validated at **FIPS 140-3 Level 3** for the current HSM type (older hsm1 clusters were FIPS 140-2 Level 3). **You** manage the users and keys, and AWS has no access to the key material. Apps use industry APIs (PKCS#11, JCE, OpenSSL/KSP). Pick it for *"dedicated/single-tenant HSM"*, *"customer must have exclusive control of the HSM"*, or regulatory mandates. It can also back a **KMS custom key store**, so AWS services still integrate through KMS while the keys live in *your* cluster. It costs more and needs more operations than KMS, so it's not the default answer.

## Question patterns

> *"A company must control who can use the key encrypting its data lake, audit every use, and rotate the key material every 180 days."* → **Customer managed KMS key with automatic rotation set to 180 days, SSE-KMS on the bucket** (AWS managed keys rotate yearly and their policy can't be edited).

> *"An application must encrypt 200 MB files before storing them, using KMS. Calls to `kms:Encrypt` fail."* → **Envelope encryption with `GenerateDataKey` (e.g., the AWS Encryption SDK)** (Encrypt accepts only up to 4 KB).

> *"After enabling SSE-KMS on a busy bucket, Glue jobs intermittently fail with KMS ThrottlingException."* → **Enable S3 Bucket Keys** (far fewer KMS calls; a quota increase is the slower, second choice).

> *"Account B's EMR cluster must read an S3 bucket in account A encrypted with SSE-KMS using the `aws/s3` key. The bucket policy already allows B."* → **Re-encrypt with a customer managed key whose key policy allows account B, and give B's role `kms:Decrypt`** (the AWS managed key can't be shared cross-account).

> *"A Redshift cluster created in 2022 is unencrypted, and auditors require KMS encryption with minimal downtime and effort."* → **Modify the cluster to enable KMS encryption** (Redshift migrates the data itself; unload/reload into a new cluster is the old, harder path).

> *"An unencrypted RDS for PostgreSQL instance must become encrypted at rest."* → **Snapshot → copy the snapshot with a KMS key → restore a new encrypted instance → cut over** (encryption can't be enabled in place).

> *"Automated snapshots of a KMS-encrypted Redshift cluster must be copied to another Region for DR."* → **Enable cross-Region snapshot copy with a snapshot copy grant for a KMS key in the destination Region.**

> *"All Athena query results across teams must be encrypted with SSE-KMS, even if users change client settings."* → **Workgroup encryption configuration with "override client-side settings" enabled.**

> *"Healthcare records must be encrypted before they leave the on-premises application so that AWS never has plaintext access."* → **Client-side encryption with the AWS Encryption SDK (or S3 Encryption Client) using KMS** (SSE-KMS still decrypts inside S3).

> *"Specific DynamoDB attributes (SSN, card number) must be encrypted client-side while other attributes stay queryable."* → **AWS Database Encryption SDK** (attribute-level; table-level SSE doesn't hide values from people who can read the table).

> *"Glue jobs connect to an Aurora database; credentials must not be in scripts and must rotate every 30 days automatically."* → **Store the credentials in Secrets Manager with rotation enabled and reference the secret in the Glue connection** (Parameter Store has no native rotation).

> *"Dozens of pipelines need environment-specific endpoints and non-secret settings, organized by environment, at the lowest cost."* → **Parameter Store standard parameters in a `/env/app/…` hierarchy** (free; Secrets Manager charges per secret).

> *"A Lambda function in account B must read a database secret stored in account A."* → **Secret resource policy allowing B's role + the secret encrypted with a customer managed key whose policy allows B + GetSecretValue in B's IAM policy.**

> *"Regulations require a single-tenant, customer-controlled HSM, but the team wants S3 and Redshift to keep using KMS integrations."* → **KMS custom key store backed by AWS CloudHSM.**

> *"Data over Direct Connect and within the VPC must be encrypted in transit to Redshift and S3."* → **Enforce TLS: `require_ssl` on Redshift and a bucket policy denying `aws:SecureTransport = false`** (KMS is at-rest encryption, and DX alone isn't encrypted).
